# Редагування листів в адмінці — стратегія

Складено 14.11.2026 на запит клієнтки. **Нічого з цього не реалізовано.** Документ фіксує, що саме
складно, що дешево, і в якому порядку це робити, коли дійде черга.

## 1. Рішення: не зараз

Поточний стан: тексти листів лежать у `src/content/mail/{ua,en}.json`, структура — у
`src/lib/server/mail/templates.ts`, оформлення — у `layout.ts` і `appearance.json`.

Три причини відкласти:

- **Черга етапів.** Дорожня карта ставить редактор після завершення адмінки й наскрізних бізнес-потоків,
  повного QA й катування. Редактор листів — новий модуль **у поштовому шляху**, тобто там, де поломку
  бачить клієнт і де її не відкотити: надісланий лист не відкликати.
- **Ціна правки зараз низька.** Зміна тексту — один рядок у JSON і `npm run mail:share` для скріна.
  Хвилини, без ризику.
- **Обсяг тестування.** Клієнтка не хоче додаткового обсягу ручного тестування; редактор його
  створює рівно там, де помилка найдорожча.

## 2. Що дешево і що дорого

**Дешево — текстові блоки без підстановок.** Вітання, пояснювальні абзаци, дрібний шрифт умов,
підпис, тексти кнопок. Це ~80% реальних правок, які клієнтка просила за останні тижні.

**Дорого — блоки, що підставляють дані замовлення** (`{number}`, суми, статус оплати, адреса,
таблиця позицій). Три окремі проблеми, кожна з яких сама по собі здатна зіпсувати лист клієнту:

1. **Змінні можна зламати руками.** Хтось зітре фігурну дужку або напише `{numbr}` — і лист піде з
   буквальним `{numbr}` або без номера. Потрібна валідація на збереженні: який набір змінних
   дозволений **у цьому конкретному блоці**, чи всі обов'язкові присутні, чи немає невідомих.
2. **Текстова версія листа генерується з тих самих даних.** Блокова модель у `layout.ts` існує саме
   для того, щоб HTML і plain-text не розійшлися. Редактор не має права цю властивість зламати.
3. **Редагування наосліп.** Без прев'ю на тестових даних прямо в панелі людина не бачить, що вийшло,
   і перевірятиме надсиланням собі — тобто ручним тестуванням, якого ми й уникаємо.

## 3. Що вже є і перевикористовується

Нічого з цього вигадувати не треба:

| Потреба                 | Готовий патерн                                                                         |
| ----------------------- | -------------------------------------------------------------------------------------- |
| Зберігання з ревізією   | `CatalogRecord` + транзакція з перевіркою `revision` (`save-record.ts`)                |
| Кеш із інвалідацією     | `unstable_cache` з тегом, як у `src/lib/server/catalog`                                |
| Двомовність із фолбеком | SEO-поля товару: редаговане значення або автоматичне                                   |
| Форма й примітиви       | `CatalogGroup`, `CatalogText`, `StaffFieldError`, `StaffConfirm`, `catalog.module.css` |
| Прев'ю                  | `scripts/preview-mail.ts` — рендерить лист без бази й без відправки                    |
| Обмеження доступу       | `catalogStaff()` (менеджер не редагує каталог — листи так само)                        |

## 4. Етапи

### M1 — тексти без підстановок (рекомендований старт)

- Колекція `mailTexts/{APP_ENV}/blocks` з ревізією; ключ = ключ зі словника (`mail.promotionOccasion`).
- Читання через `unstable_cache` з тегом; **фолбек на файл**, якщо запису немає або Firestore мовчить.
  Лист мусить піти навіть коли база недоступна — це інваріант, не зручність.
- Редактор: по блоку на локаль, поруч оригінал із файлу й кнопка «повернути як було».
- Межа: редагуються **лише** ключі з явного білого списку. Усе, що містить `{…}`, у M1 не редагується.

### M2 — прев'ю в панелі

- Кнопка «Переглянути лист» рендерить `promotionMessage` / `orderMessage` на фіксованих тестових
  даних (ті самі, що в `scripts/preview-mail.ts`) і показує HTML в `iframe` з `sandbox`.
- Без цього M3 робити не можна.

### M3 — блоки зі змінними

- Кожен редагований ключ отримує **декларацію**: перелік дозволених змінних і перелік обов'язкових.
- Валідація на збереженні (чисто, у `src/domain`, під тестами): невідома змінна → помилка поля;
  відсутня обов'язкова → помилка поля; зламана дужка → помилка поля.
- Редактор показує доступні змінні як кнопки-вставки, а не пропонує набирати їх руками.
- Таблиця позицій, суми й реквізити **лишаються в коді**. Редагується текст навколо них, не вони самі.

### Поза планом

Структура листа (порядок блоків), банер, логотип, колір, шрифти. Це дизайн-система, не контент.

## 5. Інваріанти, які не можна порушити

- Недоступний Firestore → лист іде з файлового тексту.
- Збережений шаблон **ніколи** не ламає відправку: будь-яка помилка валідації ловиться на збереженні,
  а не в момент надсилання.
- HTML і plain-text лишаються згенерованими з однієї блокової моделі.
- Користувацькі значення екрануються (`escapeHtml`) — редагований текст не стає винятком.
- Зовнішні зображення лишаються забороненими; це вже під тестом.
- Правка тексту не змінює вже надіслані листи — і це має бути написано в підказці редактора.

## 6. Орієнтовна вартість

| Етап | Частка ліміту | Коментар                                                   |
| ---- | ------------- | ---------------------------------------------------------- |
| M1   | ~10%          | Повністю на наявних патернах                               |
| M2   | ~5%           | `iframe` + уже готові тестові дані                         |
| M3   | ~15%          | Декларації, валідація, тести, редактор зі вставкою змінних |

Разом ~25–35%, не ~10%. Якщо робити частково — **M1 + M2** дають більшість користі за третину ціни
й лишають номери, суми й статуси під кодом, де їх ніхто випадково не зітре.
