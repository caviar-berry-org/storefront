# Поштові шаблони

## Чинні правила після уточнення 12.11

- Онлайн-замовлення: жодних листів до перевіреної успішної оплати. Після неї — один клієнтський лист та копії власникам. Реквізити/рахунок — листи після приймання форми. Це уточнення замінює ранній опис тригерів нижче.
- Старі невідправлені онлайн-повідомлення про створення блокуються. Старі owner jobs пригнічуються; уже надіслані листи відкликати неможливо.
- Після збереження справжньої перевіреної ТТН у сплаченому зібраному замовленні клієнт отримує лист. Довільний номер не проходить перевірку Нової пошти. Листів про отримання посилки немає.
- Подання контактної/корпоративної/подарункової форми повідомляє власника. Наявність повідомляє клієнта для потрібного фасування. DEV-одержувач власника зараз Анна; production-адреси через кому в OWNER_NOTIFICATION_EMAILS.
- Тексти робочі UA/EN, DEV відрізняється тільки [TEST] на початку теми. Таблична HTML-обгортка, inline CSS, системні шрифти, окремі відомості й footer із сайтом, offer#privacy, клікабельними контактами та Instagram/Facebook. Reply-To у production — sale@caviar.net.ua, у DEV — тестовий відправник.
- **Шапка листа (уточнення 14.11).** Клієнтські листи відкриваються емблемою бренду й слоганом під нею, як на вітрині. Емблема — PNG-CID-вкладення з `src/content/mail/logo.ts` (генерується `npm run mail:logo` з `public/assets/img/logo-emblem.svg`, 208 px, ~9 КБ): SVG більшість клієнтів вирізає, а зовнішнє посилання блокується. Листи персоналу емблеми **не мають** — там лишається текстовий напис, щоб внутрішня пошта не важчала на кожному поданні форми.
- **Візуальна мова — сторінка оформлення замовлення** (погоджено з клієнткою 14.11): тепле тло `#fbfaf7`, засічковий заголовок, великі службові підписи капітеллю з розрядкою, тонкі лінії, чорна кнопка з білим текстом. Палітра в `appearance.json` узята з токенів вітрини (`--bg`, `--ink`, `--muted`, `--line`), тож лист і сайт не розходяться. Шрифти лишаються системними: вебшрифти в пошті не вантажаться, засічки дає Georgia/Garamond.
- **Прев'ю для погодження:** `npm run mail:preview` рендерить усі листи в `.local/mail-preview/` — HTML, текстову версію й PNG для десктопа й мобільного. Нічого не надсилає: CID-вкладення підмінюються на `data:`, щоб браузер показав те саме, що складає поштовий клієнт.
- **Правки клієнтки 14.11.** Лист замовлення має три варіанти: UA «рахунок для компанії» (менеджер зв'яжеться для виставлення рахунку), UA «оплата за реквізитами ФОП» (реквізити з `src/content/payment-details.ts` + призначення платежу) і **один** EN-лист на обидва способи — так просила клієнтка, тож англомовний клієнт із переказом реквізитів у листі не бачить і чекає на менеджера. Рядок способу оплати тепер несе статус («Оплата за реквізитами ФОП — статус оплати: не сплачено»). Заголовок листа більше не містить номер замовлення (номер лишається в темі листа й першим рядком у тілі). Із футера прибрано посилання «Обробка персональних даних». Золотим виділяються: слоган, назва бренду у вітанні, підпис команди і номер замовлення в призначенні платежу.
- **Реквізити ФОП — `src/content/payment-details.ts`,** єдине джерело для листа. Фінальні значення підтверджені клієнткою 14.11.2026; IBAN перевірено (29 символів, контрольна сума сходиться, МФО 322001 = УНІВЕРСАЛ БАНК). Ті самі значення — в §15 обох оферт (`src/content/legal/{ua,en}/offer.json`), своїм формулюванням. Міняти реквізити — одразу в усіх трьох місцях; розбіжність між листом і офертою вже траплялась.
- `npm run mail:share` кладе іменовані скріни всіх листів (ПК + мобільні) на робочий стіл для погодження.
- **Зображення (уточнення 13.11).** Клієнтські листи закінчуються брендовим банером над footer. Він вшитий у лист як CID-вкладення з `src/content/mail/banners.ts` (base64, 900 px, JPEG q76, ~42 КБ на локаль), а не завантажується з сайту: зовнішні картинки більшість клієнтів блокує за замовчуванням і вони віддають відправнику сигнал прочитання. Зовнішні `<img src="http...">` лишаються забороненими — це перевіряє тест у `promotion-delivery.test.ts`. Англійський банер — те саме фото з перемальованим золотим написом (`REFINED HIGH-QUALITY CAVIAR` / `UKRAINIAN CAVIAR FARM`); перегенеровувати обидві локалі разом.
- **Листи власнику/працівникам банера не мають** і лишаються короткими (факти + посилання): вони йдуть на кожне подання форми, і трафік на це витрачати не варто.
- Макет адаптивний і враховує темну тему (`prefers-color-scheme`, клієнти без підтримки бачать світлий варіант). Перевірено від 360 px; на 320 px таблиця позицій дає ~15 px переповнення, бо суми (`1 500,00 ₴`) нерозривні — клієнт масштабує такий лист сам.
- Структура листа замовлення відповідає затвердженому макету: номер і дата, спосіб оплати, спосіб доставки й адреса, таблиця позицій, сума/промокод/знижка/разом, контакти одержувача, підпис.
- Промокод: текст умов залежить від налаштувань в адмінці — «на всі товари» або перелік назв; відсоток береться звідти ж. Формулювання про передачу коду іншій людині прибрано на вимогу клієнта (13.11).
- Лист про наявність узагальнений: текст не називає конкретну позицію (тригер і далі працює по фасуванню, посилання веде на сторінку товару).
- У листах є назва, вага, кількість, ціна одиниці, сума позиції, сума товарів, промокод/знижка й підсумок. Дані беруться зі знімка замовлення. У mono передаються назви з вагою та точні нетто-суми; округлення розподіляється між одиницями. Зображення у payload немає; порожню мініатюру може малювати сама сторінка mono.

- `ua.json`, `en.json` — тексти листів клієнтам. Тексти `owner.*` з українського файла — повідомлення власнику. `{name}`, `{product}`, `{code}`, `{percent}`, `{date}` залишайте як змінні.
- `appearance.json` — спільні inline CSS для HTML-листів: фон, шрифт, ширина, відступи. Структура листів і склад даних — `src/lib/server/mail/templates.ts`. Користувацькі значення екрануються; текстова версія генерується разом з HTML.
- Зміни файлів потребують нової збірки. Уже відправлені листи не змінюються. SMTP `accepted` означає приймання поштовим сервером, а не підтвердження прочитання чи потрапляння у вхідні.

## Середовище

```dotenv
OWNER_NOTIFICATION_EMAILS=kotlyaranya1771@gmail.com
OWNER_EMAIL_ENABLED=true
RESTOCK_EMAIL_ENABLED=true
```

Кілька адрес власників задавайте через кому, наприклад `sale@caviar.net.ua,other@example.com`. Кожен одержувач отримує окрему копію. Для DEV зараз налаштована лише адреса розробниці для тесту. В проді будуть всі сповіщення йти на пошти працівників і замовниці `sales@faic.com.ua` та `faic.caviar@gmail.com`
SMTP і Firebase середовища лишаються розділеними. Нове замовлення/заявка та поштові завдання записуються атомарно; збій SMTP не відкочує прийняту заявку. Автоматичні повтори — тільки для однозначно невідправлених листів: до трьох спроб, інтервал від хвилини. Невідоме приймання або невдале збереження результату SMTP не запускає автоматичного дубля.

Лист власнику створюється для нового замовлення ікри, подарункової/корпоративної заявки та звернення. Після збереження залишків або зміни видимості ікри перевіряються очікування наявності й створюються одноразові завдання для доступного товару/фасування. Тестові записи `test: true` пропускаються. Черга бере по 20 готових завдань, відправляє по 4 паралельно й продовжує обробку в межах часу функції. Незавершені завдання лишаються в черзі. Приватний `/api/internal/reconcile` з `CRON_SECRET` підбирає чергу та безпечні повтори; чинний розклад — раз на добу. Для більш частого відновлення після збоїв потрібен частіший зовнішній виклик цього endpoint. Нові події запускають відправку одразу після приймання запиту; Vercel має отримати ті самі змінні середовища.

Запити на наявність до цієї зміни без збереженої мови використовують українську; нові зберігають UA/EN клієнта. Шаблон рекомендує перевірити актуальний залишок на сайті, адже наявність може змінитися до відкриття листа.
